# LLM Reporting Module


---

## Overview

The LLM module is the final reporting and reasoning component of the thesis project.

It does **not** analyze raw iEEG signals directly. Instead, it consumes structured JSON summaries generated by two upstream branches:

1. **HFO detection branch**
2. **Seizure detection branch**

The LLM system receives these structured outputs, performs reasoning over them, compares findings between the two branches when possible, and generates a human-readable iEEG report.

The LLM reporting pipeline was developed in four versions:

| Version | Main Purpose |
|---|---|
| Version 1 | Initial report generation from HFO and seizure JSON summaries |
| Version 2 | Channel-level seizure evidence and deterministic HFO-seizure fusion |
| Version 3 | Schema-validated reasoning and deterministic report rendering |
| Version 4 | Bounded tool orchestration and planner-based execution |

---

## Folder Structure

```text
src/llm/
  version_1/
  version_2/
  version_3/
  version_4/
  README.md
```

Each version represents a separate development stage of the LLM reporting system.

Additional subject case studies for the final Version 4 pipeline should be placed inside `version_4/`, not as separate versions.

Example:

# Version 1

## Purpose

Version 1 is the first unified LLM reporting pipeline.

The main goal of this version was to combine HFO and seizure JSON summaries into a single subject-level case and use a local LLM to generate a structured report.

This version introduced:

- subject-level HFO summary input;
- ictal and interictal seizure summary input;
- master case JSON construction;
- compact LLM input construction;
- two-stage LLM generation:
  - reasoning JSON generation;
  - final report generation.

---

## Main Limitation

Version 1 does not support strong direct HFO-seizure channel concordance analysis.

The reason is that seizure channel-level evidence is not available in the same structured form as in later versions. Therefore, Version 1 can compare HFO findings with seizure-run behavior, but it should not make strong claims about direct overlap between HFO channels and seizure-supportive channels.

---

## Main Scripts

### `build_master_case.py`

Builds the integrated subject-level master case from HFO and seizure JSON summaries.

Expected output:

```text
sub-HUP146/integration/sub-HUP146_master_case.json
```

### `run_llm_case.py`

Runs the LLM report-generation pipeline.

The script usually performs the following steps:

1. Loads the master case.
2. Builds compact LLM input.
3. Calls the LLM for structured reasoning.
4. Saves raw reasoning output.
5. Parses reasoning JSON.
6. Calls the LLM again for final report generation.
7. Saves the final text report.

---

## How to Run Version 1

From the `version_1` folder:

```bash
python build_master_case.py
python run_llm_case.py
```

Important: early scripts may contain local absolute paths such as:

```text
D:\LLM_unified_HUP
```

If needed, update these paths to match the repository location.

# Version 2

## Purpose

Version 2 improves Version 1 by adding stronger deterministic integration between HFO and seizure outputs.

This version introduced:

- channel-level seizure evidence;
- deterministic fusion logic;
- cross-modal comparison between HFO candidate channels and seizure-supportive channels;
- explicit concordance and mismatch flags;
- improved compact LLM input construction;
- reasoning JSON repair pass when needed.

---

## Main Improvement

Version 2 allows a more meaningful comparison between the HFO branch and the seizure branch.

Unlike Version 1, it can report whether HFO candidate channels overlap with seizure-supportive channels. This makes the generated report more clinically useful because the report can explain whether both biomarkers point toward similar electrode regions.

# Version 3

## Purpose

Version 3 improves reliability, structure, and reproducibility.

This version introduced:

- modular Python package structure;
- schema-validated reasoning JSON;
- reasoning repair prompt;
- deterministic report rendering;
- separate scripts for pipeline, reasoning, and report generation;
- cleaner input/output organization.

---

## Main Improvement

Version 3 reduces dependence on free-form LLM output.

The LLM still performs reasoning, but the final report is no longer generated only as free text. Instead, the system validates structured reasoning JSON and then renders the final report deterministically from the validated JSON.

This makes the report generation process more stable, easier to debug, and easier to reproduce.

# Version 4

## Purpose

Version 4 is the final and most complete LLM reporting system.

It extends Version 3 with bounded tool orchestration and planner-based execution.

Version 4 introduced:

- planner LLM;
- planner schema validation;
- tool registry;
- tool executor;
- bounded tool execution;
- orchestration state tracking;
- tool execution logs;
- ability to rebuild master case, rebuild compact case, rerun reasoning, and regenerate report through a controlled tool plan.

---

## Main Improvement

Version 4 changes the system from a static pipeline into an adaptive orchestrated pipeline.

Instead of simply running all steps in a fixed order, the system allows a planner to decide which tools should be executed. However, the planner is constrained by a predefined tool list and schema validation, so tool execution remains bounded and auditable.

## Available Tools

The Version 4 planner can call a bounded set of tools.

| Tool | Purpose |
|---|---|
| `rebuild_master_case` | Reconstructs the full multimodal case from HFO and seizure outputs |
| `rebuild_compact_case` | Produces a reduced LLM-ready compact case |
| `run_reasoning` | Runs schema-constrained reasoning and validation |
| `run_report` | Regenerates the final structured report |

The tool set is intentionally limited. This makes the orchestration behavior easier to inspect, validate, and reproduce.

# LLM Backend

The code was developed for local inference through Ollama.

Default model:

```text
qwen3:8b
```

Default Ollama endpoint:

```text
http://127.0.0.1:11434/api/generate
```

Before running the scripts:

```bash
ollama pull qwen3:8b
ollama serve
```

Other Ollama-compatible models can be used by changing the `--model-name` argument.

# Input Files

Each subject folder expects HFO and seizure JSON summaries.

## HFO Input

```text
sub-HUPXXX/hfo/
  sub-HUPXXX_hfo_subject_summary_for_llm.json
```

This file summarizes:

- subject ID;
- sampling frequency;
- detector settings;
- run IDs;
- ripple detections;
- fast ripple detections;
- FRandR detections;
- channel-level HFO rates;
- HFO area;
- cross-run aggregated HFO evidence.

## Seizure Input

```text
sub-HUPXXX/seizure/
  sub-HUPXXX_*task-ictal*_seizure_summary_for_llm.json
  sub-HUPXXX_*task-interictal*_seizure_summary_for_llm.json
```

These files summarize:

- run ID;
- task type;
- window-level counts;
- predicted-positive fraction;
- smoothed seizure probabilities;
- threshold used;
- candidate ictal segments;
- channel-level seizure evidence;
- run-level interpretation.

# Notes on Reproducibility

LLM outputs may vary slightly depending on:

- Ollama version;
- Qwen model version;
- decoding parameters;
- operating system;
- hardware;
- prompt changes.

For this reason, the repository stores:

- raw LLM outputs;
- validated reasoning JSON;
- validation reports;
- deterministic final reports;
- orchestration logs for Version 4.

These artifacts make it easier to inspect what the model generated and what was accepted by the validation and rendering pipeline.
